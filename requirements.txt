# 2.3.8 exactly, not >=2.3.8: send_node_discover_req / req_regions_sync (zero-hop
# neighbour discovery) and the bounded, serialised BLE write both landed at 2.3.8,
# so we can't go lower. But 2.3.10 (serial_cx.py) added an unconditional
# `transport.serial.dtr = False` on every serial connect, alongside the existing
# `rts = False`. On boards where DTR/RTS are wired through the standard
# esptool-style auto-reset circuit (EN + GPIO0), toggling both together can pulse
# the chip into UART bootloader/download mode instead of a normal boot -- a
# silent regression (2026-09-14) that reproduced as "No response from meshcore
# node" on serial-connected companions even though the device was otherwise
# healthy (confirmed alive and forwarding mesh traffic when probed outside the
# meshcore-py connection path). Pinned exactly until upstream fixes/reverts this;
# unpin only after confirming the DTR toggle is removed or made opt-in.
#
# Upstream (2026-09-27 merge) wants >=2.3.14 instead, for a real, unrelated fix:
# before 2.3.13, send_msg_with_retry reported ACKed DMs as failures (subscribed
# to the ACK only after send_msg returned, and each attempt accepted only its
# own ACK code, so an ACK arriving right behind MSG_SENT or answering an earlier
# attempt was ignored -- meshcore_py#108); 2.3.14 also fixes send_cmd's
# destination-type handling. NOT taken here without testing on real hardware
# first: 2.3.14's create_serial() changes dtr from 2.3.10's forced False to a
# configurable parameter defaulting to True -- our call site (core.py,
# create_serial()) does not pass dtr, so upgrading would silently move from
# "dtr untouched" (2.3.8) to "dtr asserted True" (2.3.14 default), which is a
# third, unverified state on the affected boards -- not simply a revert of the
# known-bad 2.3.10 behavior. Re-evaluate after confirming on the actual
# serial-connected companions.
